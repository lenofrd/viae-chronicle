# 001 - 采用事件溯源（Event Sourcing）与 SQLite 存储

- **状态**：已采纳 (Accepted)
- **日期**：2026-11-14
- **决策者**：架构组

## 1. 背景与上下文 (Context)
Vale Chronicle 是一个常驻运行的文字模拟器，核心需求是：
1. **连续演化**：系统需要长期（数万至数十万 Tick）不间断运行。
2. **完整记录**：需要能随时调取任意角色从出生到死亡的所有经历。
3. **因果可追溯**：环境的变化、人物的决断、纠纷的爆发，都必须能向上追溯到触发它的父事件。
4. 本地单机运行，轻量优先。

## 2. 决策 (Decision)
我们决定放弃传统的“仅保存当前状态”的做法，采用 **事件溯源（Event Sourcing）** 架构：
1. **唯一真相**：所有状态变化必须以“事件（Event）”的形式追加记录，不可修改、不可删除。
2. **存储引擎**：采用 **SQLite** 作为单一持久化数据库，不依赖外部服务。
3. **快照机制（Snapshotting）**：为了避免查询时从头重放几十万条事件导致的性能灾难，每隔一定的 Tick 数（如 100）或重大节点，保存一份实体的全量状态快照。

## 3. 后果与影响 (Consequences)

### 优势：
- **绝对的可追溯性**：任何角色的“一生”只需在 `events` 表里按 `actor_id` 过滤并排序即可原样呈现。
- **可重放性（Replayability）**：修复 Bug 或测试新规则时，可以使用完全相同的初始条件和历史事件，完美复现过去的演化轨迹。
- **调试便利**：通过 `cause_id` 可以生成一棵完整的因果树，直观看到“为什么发生了旱灾 -> 为什么发生了水权纠纷 -> 为什么某人被打”。

### 代价：
- **写入开销**：每次状态变化都会产生磁盘 I/O（尽管 SQLite 配合事务可以缓解）。
- **查询组装**：要获取当前状态，需要结合最近的 `snapshot` 和其后产生的事件进行组装，这要求代码里有一层状态重放逻辑（`rebuild_state`）。
- **状态一致性**：所有的模块在修改状态时，必须通过 `EventLog` 发起，严禁直接修改内存中的全局变量（否则会导致数据库和内存脱节）。

## 4. 替代方案被拒绝的原因
- **纯 JSON/文本日志**：数据量达到几十万条时，无法做高效的索引过滤和范围查询。
- **MySQL/PostgreSQL**：对于单机常驻模拟器而言，部署和维护成本过高，且 SQLite 完全足够。
- **仅存当前状态（传统 CRUD）**：会彻底丢失历史轨迹，直接违背了本项目“查看个体一生经历”的核心初衷。
